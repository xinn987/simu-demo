## 2. S1：最小落沙模型

来源：[S1](https://jason.today/falling-sand)。

### 2.1 原文的构建过程

1. 使用一维数组表示二维网格，索引关系为 `index = y * width + x`。最初用颜色表示沙、用 `0` 表示空位。
2. 鼠标操作向网格写入材料，显示循环再将网格转成像素。
3. 第一条规则是：下方为空，就与下方交换位置。
4. 从上往下原地更新时，沙的新位置尚未被扫描，因此同一颗沙会在一轮内反复下落，看起来像直接出现在底部。
5. 改为从下往上扫描，使下落后的格子已经被扫描，避免这种重复处理。
6. 加入左下、右下候选位置，使沙可以堆积和滑落，而不只是形成竖直柱子。
7. 用圆形、带生成概率的笔刷改善投放观感，并在生成时轻微改变颜色饱和度和明度。

核心认识：局部规则能产生堆积形态，但规则的执行顺序也是模拟结果的一部分。

### 2.2 对本项目的参考

当前项目已经采用一维紧凑数组、从下往上扫描、下落与斜落、圆形笔刷。与文章初版不同，材料身份和显示颜色已经分开，左右斜落的优先顺序也使用独立随机数发生器选择。

- [GridWorld](../../simulation/grid_world.gd)：网格索引、封闭边界、成对修改来源与目标。
- [SandSimulation](../../simulation/sand_simulation.gd)：扫描顺序和三种移动尝试。
- [实验室控制器](../../laboratory/laboratory.gd)：圆形笔刷、连续笔划。

颜色差异和概率投放可作为以后改善观感的候选项，当前不必优先加入。颜色变化应使用独立的视觉随机数或稳定的颜色变体，避免修改配色后改变材料运动的随机序列。

### 2.3 不能泛化的地方

“从下往上就不会重复更新”仅适用于这种始终下移的运动。向上的烟雾、水平水流、材料交换和反应生成新材料，都需要重新分析更新次数。

原文早期步骤是刻意简化的教学中间版本，后续 S2 才补充横向越界等问题。不能把某个步骤的片段直接当作完整的通用网格实现。

## 3. S2：从性能测量到速度模型

来源：[S2](https://jason.today/falling-improved)。

### 3.1 材料应拥有独立身份

原文从“格子里只有颜色”改成 `Particle` 对象，并派生沙、空位和木材，以便保存属性和执行不同规则。

值得借鉴的是把材料身份、属性和行为区分开。原文为每格创建对象的具体做法不是本项目的要求：目前保留材料编号数组；未来按实际需要增加速度、液体量、温度等独立数组。发生移动、交换或反应时，相应状态也必须跟随或重置，不能只搬材料编号。

### 3.2 优化之前先测量

作者使用浏览器性能分析工具，发现大量时间消耗在颜色字符串解析上：每一帧、每个像素、每个颜色通道都重复解析。将颜色预先转换为可直接使用的对象后，减少了这项开销。

这说明应先定位瓶颈，再选择优化方向；并不说明 Godot 项目也有相同瓶颈。本项目的调色板已经保存为 `Color`，没有在逐格更新中反复解析颜色字符串。

后续应分别测量模拟扫描、CPU 图像写入和纹理上传的耗时，不应把所有耗时归为“粒子太多”。

### 3.3 变化像素、显示更新与停止空转

原文通过统一的网格写入口记录 `modifiedIndices`，绘制时只改写这些像素；清空则走全量刷新。没有更新且没有用户操作时，使用 p5.js 的停止循环机制休眠，输入事件再恢复循环。

需要区分三个层次：

| 层次 | 解决的问题 | 与本文及本项目的关系 |
| --- | --- | --- |
| CPU 像素更新 | 少修改图像缓冲中的像素 | S2 的变化索引集合主要用于这一层 |
| 图像提交与绘制 | 少上传纹理或少绘制 | S2 另讨论停止循环；变化索引本身不保证局部 GPU 上传 |
| 模拟更新 | 少检查不可能变化的格子 | 活跃格子、区块和邻居唤醒是进一步设计，不能说 S2 已实现这些机制 |

当前 `GridWorld.revision` 能让 `GridView.refresh_texture()` 在世界未变化时跳过图像重写与上传；只要世界变化，仍然重写完整图像并调用 `ImageTexture.update()`。与此同时，未暂停的模拟仍扫描全图。

迁移时先确认耗时：即使只修改 `Image` 的部分像素，也不能据此认定 `ImageTexture.update()` 只上传该区域。是否采用分块纹理或其他提交方式，需另行测量与设计。

### 3.4 减少扫描偏差并防止跨行越界

原文保留从下往上的行顺序，但为每一行随机选择从左向右或从右向左扫描。它还检查斜下目标所在列，避免数组加减一后从屏幕一侧绕到另一侧。

本项目采用的是“每步交替整张网格的横向扫描方向 + 随机斜落优先级”，与原文每行随机扫描不同。两者都试图减少固定方向偏差，但不能默认当前方案或原文方案一定更好。

若后续发现偏差，可以用相同投放条件、多组种子比较沙堆左右数量与质心；单张看起来对称的截图不足以证明无偏。边界则继续通过二维坐标检查统一处理。

### 3.5 速度、加速度与移动子步

原文增加一维速度：每轮增加加速度，限制最大速度，运动受阻时将速度归零。速度决定本轮执行多少次相邻格移动。

小数速度采用概率取整：

```text
移动子步数 = floor(abs(v)) + 一次概率为 frac(abs(v)) 的 0/1 抽样
```

例如 `v = 1.5` 时，每轮执行 1 或 2 次子步，各有一半概率；`v = 0.25` 时，约四分之一的轮次执行一次。未受阻时，其期望子步数等于速度绝对值，但单次轨迹会有随机波动。

每次子步都从粒子的新位置继续检查下一格，遇到阻挡就停止。这与直接跳到远处终点不同，能检查沿途占用。它仍是格子运动模型，不是连续空间中的刚体或流体求解器。

迁移建议：

- 区分“一次全局模拟步”和“其中多次移动子步”；不能把加速度、寿命和反应也无意执行多次。
- 每次全局更新先确定本次子步数，再执行移动，避免在循环条件里反复进行随机取整。
- 初期可把速度定义为“格/模拟步”，加速度定义为“格/模拟步²”；若改用秒，需要明确固定时间步换算。
- 原文给出的最大速度和加速度是其演示参数，不是可直接迁移的物理常数。
- 小数速度本步抽到零次移动，不代表材料已经静止。自动休眠必须考虑这种未来仍会变化的状态。

## 4. S3：烟雾、行为组合与燃烧

来源：[S3](https://jason.today/falling-fire)。

### 4.1 用行为组合减少继承分支

原文把运动、寿命和可燃性拆成 `Behavior`，一个粒子按既定顺序执行多个行为。例如烟雾可以同时拥有移动和有限寿命，木材则拥有可燃性。

本项目可借鉴行为职责分离和明确执行顺序，不必照搬为“每格挂多个脚本对象”，也不必立即实现通用组件框架。材料增多后，可以将运动、传热、反应分成明确阶段，再根据真实重复逻辑决定是否抽象。

### 4.2 烟雾上升与双向扫描

原文先让运动方向由速度正负决定，使烟雾向上。但继续从下往上扫描，会再次出现一轮中多次处理同一材料的问题。

随后使用正反两趟扫描：向下运动与向上运动分别在适合的扫描方向更新，并通过 `Moves.shouldUpdate()` 判断当前行为是否属于该趟。

这是理解调度的好例子，但迁移时不能只复制两趟循环。还需要定义：

- 生命周期、燃烧和颜色更新每个全局步执行几次。
- 水平运动、方向改变和材料交换后，是否可能再次被扫描。
- 本步新产生的烟、火或产物，是否允许立即参与后续更新。

原文的方向过滤在运动行为中，不能自动为所有行为提供“一步一次”的保证。项目后续可比较按阶段执行、更新时间标记和其他调度方式，先明确语义再选择实现。

### 4.3 从空位判断到材料通过条件

原文将 `isEmpty` 扩展为 `canPassThrough`：烟带有 `airy` 属性，沙可以与烟所在位置交换，而烟仅通过空位。

这提供了一个明确的材料关系，但还不是完整的密度、混合或溶解模型。后续增加油水分层等行为时，应分别定义阻挡、交换、混合和反应；只比较一个密度数值并不能决定全部关系。

### 4.4 有限寿命、淡出与持续活跃

`LimitedLife` 保存总寿命与剩余寿命，更新时推进计时，通过回调改变显示或处理死亡。烟雾随剩余寿命降低透明度，寿命结束后清除。

即使烟被困住没有位移，它仍然需要继续计时与更新显示。因此原文会标记它发生修改，避免循环提前停止。

对本项目有两项直接启发：

1. “位置没变”不等于“不需要更新”。热交换、燃烧、倒计时和设施任务也属于持续活动。
2. 烟雾淡出后删除是一条效果规则，不是自动成立的质量守恒过程。未来若气体参与生产、储存或化学反应，就要单独设计其数量与去向。

### 4.5 燃烧传播与火星

原文按以下步骤扩展效果：

- 先做有限寿命、颜色闪动的火，结束时转成烟。
- 加入 `burning` 状态、燃料寿命和点燃概率。未燃烧的木材不消耗燃烧寿命。
- 燃烧材料影响周围候选格，向可燃邻居累计点燃机会；邻近火源越多，点燃倾向越高。
- 候选邻域需要检查数组边界和跨行问题。
- 再调节传播概率，并让部分烟状粒子带有燃烧状态、向上或向下运动，形成能够远距离点燃材料的火星效果。

这是寿命、概率传播与视觉变化组合成的燃烧模型，不包含完整的温度场、氧气消耗、比热、潜热或化学计量。未来的工业反应应另行约定输入、产物、热量与生成空间不足时的处理。

迁移时还需把概率与固定模拟步绑定，明确八邻域是否排除中心格，并规定传播影响何时生效。否则扫描方向、两趟更新或刚生成的火，都可能改变传播速度。

## 6. 候选优化与实验清单

下面是供未来讨论使用的参考顺序，不是已批准的实施排期。保持项目既定主线：先完善实验室中的材料规律，再发展设施与流水线。

| 时机 | 候选工作 | 最小验证条件 |
| --- | --- | --- |
| 性能优化之前 | 分别记录模拟、图像写入与上传耗时 | 固定尺寸、种子、材料数量和硬件条件，保留基准 |
| 出现明显视觉方向偏差时 | 比较扫描策略 | 多种子统计左右分布；守恒、边界结果不退化 |
| CPU 图像更新成为瓶颈时 | 引入变化格索引或脏区域 | 静止画面、移动两端、擦除、清空、重置均无残影；确认实际耗时下降 |
| 静止场景计算成为瓶颈时 | 设计休眠及邻居唤醒 | 移除支撑、投放材料后恢复；低速粒子、热与寿命不会被提前冻结 |
| 需要加速下落时 | 引入速度、加速度和子步 | 高速粒子不穿过一格厚的墙；受阻规则清晰；固定种子可复现 |
| 引入气体或水之前 | 明确多方向运动与更新次数 | 上下运动不会瞬移；水平移动和交换不重复处理；寿命每步只推进约定次数 |
| 建立第一条燃烧链时 | 定义可燃状态、燃料、传播与产物 | 不着火的木材不被消耗；阻隔、边缘和产物占用行为符合约定 |

性能收益必须来自项目实测；不能把浏览器演示中的改进幅度直接当作 Godot 的收益。液体数量、压力、温度和工业配方也不是这三篇已经解决的问题，需要后续单独研究。

## 7. 后续使用方式

每次准备采用其中一项时，先明确要改善的现象，定位本项目代码和原文对应段落，再讨论最小改动与验收条件。得到开始指令后实施，使用同一实验条件验证行为与性能，并更新本页状态。

实验室继续作为验证场地；代码学习使用 Godot 编辑器、断点和项目说明，不因文章带有交互教学演示而增加专门的教学界面。
